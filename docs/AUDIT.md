## PERF-1 성능 진단 (G4W3, 2026-11-05)

실험실 측정이다. 실제 기기와 현장 데이터는 미검증이다. 수치는 모두 m390(390×844, DPR 2, 카카오톡 iOS UA)에서 쟀다. 네트워크는 CDP 지연 150ms·1.6Mbps 하향·750Kbps 상향이다. `next start` 서버를 쓰고 `--workers=1`로 한 번에 하나만 돌렸다. '진단'은 테스트와 같은 흐름을 도는 일회용 스크립트다(커밋 안 함). 이 스크립트는 LCP 후보, 리소스 타이밍, `event` 항목, Long Animation Frames를 모은다. '공식'은 `tests/perf.spec.ts`다. 표의 값은 중앙값이고 괄호는 범위다.

**inlineCss 시도와 되돌림**: 아래 'inlineCss 시도'는 `experimental.inlineCss`를 켰다가 되돌린 빌드(커밋 5fb8b09, 되돌림 f580f91)다. 현재 코드는 '변경 전'과 같다.

### 호스트 상태

- i7-8565U(4코어 8스레드, 저전력 노트북), RAM 16GB. 배치 직전 여유 RAM은 2,723–4,128MB였다. WSL·Docker Desktop·사용자 Chrome·카카오톡이 실행 중이었다.

### 결론과 권고

- 상태: 열림(미해결). 현재 코드(변경 전과 같음) 기준 실험실 결과: LCP는 기준 언저리(3회 묶음 중앙값 2320 / 2680 / 2760ms, 9회 중앙값 2680), INP는 실패(묶음 중앙값 376–456ms, 9회 중앙값 408). CLS는 통과한다. 이 호스트의 실험실 수치는 노이즈가 매우 크다. 실제 기기, 현장, Lighthouse는 미검증이다.
- R1(사용자 승인 필요). 글꼴을 실제로 쓰는 글자(약 300자)만 담은 사용자 정의 서브셋으로 바꾸고, 글꼴마다 `@font-face`를 1–2개로 줄인다. 기대 효과는 CSS −29KB(gzip), 글꼴 요청(상품 화면 17개 377KB, 이후 화면 6개 123KB)을 2–3개로 줄이는 것이다. 또 `GetFontPlatformData` 호출이 대부분 사라지고, 화면 전환 레이아웃이 글꼴 제거 실험 수준(CTA 144ms)에 가까워질 것으로 본다. 다만 서브셋 도구(fonttools)가 새 의존성이다. 글리프 픽셀 일치를 확인해야 하고, 문구를 바꿀 때마다 서브셋을 다시 만들어야 한다.
- R2(판단 필요). 실험실 CPU 배율을 호스트에 맞게 보정하거나(Lighthouse 방식), 실제 기기 측정으로 판단한다. 이 호스트에서 '4배'는 실측 4.5–8배이고, 1배에서는 LCP 1512 · INP 40ms로 여유 있게 통과한다. 기준값은 바꾸지 않았다.
- R3(승인 필요, 화면 변화). 히어로 `placeholder="blur"`가 LCP 항목이 되기도 한다. 없애면 로딩 중 화면이 바뀐다. LCP가 선명한 사진 기준이 되어 더 정직해지지만 빨라지지는 않는다.
- R4. CSS 인라인(`experimental.inlineCss`): FCP 개선 가능성은 있으나, HTML +74KB·실험 기능·공식 측정에서 노이즈 범위라 보류한다. 시도했다가 되돌렸다(5fb8b09 → f580f91). 진단 스크립트의 개선 일부는 LCP 항목이 블러 자리표시자로 바뀐 데서 온 착시다.
