> 무엇을 어떻게 검증하고, 언제 '완료'와 '공개'로 판단하는지 정한다. 요구사항은 [PROJECT.md](PROJECT.md), 화면 기준은 [DESIGN.md](DESIGN.md), 테스트 코드는 [PLAN.md](PLAN.md) 각 Task에 있다.

## 1. 원칙

- **기능 테스트 통과만으로는 완료가 아니다.** 모든 화면 작업은 실제 브라우저 스크린샷 검증(§7)과 디자인 감사(§8)를 함께 통과해야 한다(NFR-8).
- 테스트는 결정적이어야 한다. 난수(`Math.random`)와 시계(`page.clock`)를 고정하고, 폰트와 이미지는 자체 호스팅한다.
- 자동화할 수 없는 것은 실기기로 확인하고 기록한다: 카카오톡 인앱 브라우저, 스크린리더, 체감 속도.
- 결과는 `docs/AUDIT.md`에 날짜와 근거를 붙여 남긴다(§12).

## 4. 게임 상태 전이 테스트

PLAN '상태 전이' 표의 모든 행을 단위 테스트로 덮고, 사용자 경로는 E2E로 한 번 더 확인한다.

| 전이 | 단위(`lib/game.test.ts`) | E2E |
|---|---|---|
| product → select (`start`) | 정상 흐름 | flow ② beforeEach |
| select: `pick`, `begin`(조건) | 정상 흐름, 고르기 전에는 시작 불가 | flow ② |
| select → product (`back`) | 뒤로 | flow ② '뒤로' |
| measure: `tap` ≤ 5 | 5회를 넘는 탭 | flow ③ |
| measure → result (`finish`, taps=5만) | 5회 전에는 결과로 가지 않음 | flow ③ |
| measure → select (`back`, taps=0) | 뒤로 | flow ③ '뒤로' |
| result → judging → ending | 정상 흐름 | flow ⑤ |
| result·ending → select (`retry`) | 다시 검사 | flow ④·⑥ |
| 맞지 않는 화면의 이벤트 무시 | 맞지 않는 화면의 이벤트 | — |
| 당도 배정 6가지 모두 가능, 값 보존 | assignBrix 2건 | flow ④ random=0 |

**기준:** 단위 12건 통과, 경고 없음. 리듀서를 고치면 반드시 단위 테스트를 먼저 수정한다(TDD).

## 7. Playwright 시각적 회귀 테스트

- **기준 이미지:** `tests/__screenshots__/m390/*.png`, `m360/*.png` 각 8장(상품, 수량 시트(2박스), 안내 모달, 선택(C 선택), 측정(3/5), 결과, 판정 전환(최종 프레임), 엔딩)
- **고정 조건**
  - `Math.random = 0.999`(A 12.4 · B 14.2 · C 15.8)
  - 시계 2026-11-05 10:00 KST
  - 애니메이션 비활성(최종 프레임), 로케일 ko-KR, 라이트 모드
- **허용 오차:** `maxDiffPixelRatio: 0.01`. 작은 문구 변경은 1% 안에 숨을 수 있으므로, 디자인을 바꿀 때는 `--update-snapshots=all`로 전부 다시 만들고 이전 이미지와 픽셀 비교로 바뀐 장을 확인한다(T19)
- **기준 생성 절차:** PLAN T10 Step 2~3. 생성한 12장을 승인 시안(`docs/design/shots2`)과 나란히 사용자에게 보이고, **승인 후에만** 커밋한다.
- **갱신 규칙:** `--update-snapshots`는 사용자가 승인한 디자인 변경에만 쓴다. PR 설명에 변경 전후 이미지를 붙인다. 이유 없는 갱신은 금지한다.
- **환경:** 기준 이미지는 같은 OS(로컬 Windows)에서 만든다. CI를 도입하면 CI 환경에서 다시 만들고 다시 승인받는다.
